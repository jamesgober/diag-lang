# diag-lang v1.1.0 — codes, fix-its, JSON, and a collector

**Additive minor release.** A diagnostic can now carry a stable error code and
fix-it suggestions; the renderer shows both rustc-style; a helper applies the
safe fixes to a source; the same diagnostics come out as versioned,
deterministic JSON; and a collector gathers a compilation's diagnostics with
counts, duplicate suppression, sorting, and a cap. This is ISSUES M19, plus the
diag-lang side of P04 (codes for the forge) and P19 (lexical errors get their
own code range). Every API change is additive: code that builds against 1.0
builds unchanged, and a diagnostic without a code or suggestions renders byte
for byte as in 1.0.1.

## What is diag-lang?

The diagnostics layer of a compiler front end. It collects diagnostics — a
severity, a message, and labelled spans — and renders them with source context,
a caret underlining exactly where the problem is. Positions come from
`span-lang`, source text from `source-lang`. It is `no_std`-compatible and
`#![forbid(unsafe_code)]`.

## What's new in 1.1.0

### Error codes

A `Code` is the stable name of a kind of diagnostic: one to four uppercase
letters (the registry) and exactly four digits. `Code::new` is `const`, so a
registry declares its codes as constants checked at compile time:

```rust
use diag_lang::{Code, Diagnostic, Label, Renderer, Severity, SourceMap, Span};

const UNKNOWN_NAME: Code = Code::new("E", 425).unwrap();

let mut map = SourceMap::new();
map.add("main.rs", "let x = foo();").unwrap();
let diag = Diagnostic::new(
    Severity::Error,
    "cannot find value `foo` in this scope",
    Label::new(Span::new(8, 11), "not found in this scope"),
)
.with_code(UNKNOWN_NAME);

assert!(Renderer::new()
    .render(&diag, &map)
    .starts_with("error[E0425]: cannot find value `foo` in this scope\n"));
assert_eq!(Code::parse("E0425"), Some(UNKNOWN_NAME));
```

`docs/API.md` has a guide to code registries: the codes the family already uses
(OPS `E0001`–`E0099`, LSB `E0100`–`E0199`, typeck `T0001`–), and a recommended
split within a language's own prefix — lexical `0001`–`0999`, parse
`1000`–`1999`, semantic `2000`–`7999`, lints `8000`–`8999`, internal
`9000`–`9999`. With it, "is this a lexical error?" is `code.number() < 1000`,
not a guess from the message text (P19).

### Fix-it suggestions

A `Suggestion` is a message, a set of `Edit`s (a span and its replacement), and
an `Applicability` with rustc's four levels. The renderer shows the fixed lines:

```text
error[E1001]: expected `;`
 --> calc.ls:1:22
  |
1 | let total = count + 1
  |                      ^ statement ends here
  |
help: add `;`
  |
1 | let total = count + 1;
  |                      +
  |
```

`+` marks inserted text and `~` replacement text. When an edit only deletes, the
block is a diff — the old lines marked `-`, the new ones `+`, with lines the two
share left out, so removing a whole line shows just that line:

```text
help: remove the binding
  |
3 - let unused = 2;
  |
```

Edits in another source get their own block headed `--> file:line:col`; blocks
over five lines are elided like long spans; a suggestion that cannot be placed
(out of bounds, splitting a character, overlapping edits) shows its message
alone. Replacement text is escaped like all other text.

### Applying fixes

`apply_fixes(text, base, diagnostics)` applies every machine-applicable
suggestion that targets `text`, and `apply_edits(text, base, edits)` applies
any set of edits. Edits are checked against the text's bounds and UTF-8
boundaries, sorted, and conflict-checked; identical edits are applied once;
on any problem nothing is applied and an `ApplyError` says which edits:

```rust
use diag_lang::{Applicability, Diagnostic, Edit, Label, Severity, Span, Suggestion, apply_fixes};

let text = "let x = 1\nlet y = 2\n";
let missing_semi = |at: u32| {
    Diagnostic::new(Severity::Error, "expected `;`", Label::unlabelled(Span::empty(at)))
        .with_suggestion(
            Suggestion::new("add `;`", Applicability::MachineApplicable)
                .with_edit(Edit::insert(at, ";")),
        )
};
assert_eq!(
    apply_fixes(text, 0, &[missing_semi(9), missing_semi(19)]).unwrap(),
    "let x = 1;\nlet y = 2;\n",
);
```

### JSON output

`Diagnostic::to_json(&map)` writes one line of JSON; `Diagnostics::to_json(&map)`
writes one document with error and warning counts. No dependency, compact,
fixed key order, RFC 8259 escaping (plus U+2028/U+2029), and a `"version": 1`
key. Each label and edit carries its global byte span and a resolved location —
file, and byte offset, line, and column for each end — so an LSP server can
convert to UTF-16 and an AI client can quote the source. The schema is
documented in `docs/API.md#json-output`; within version 1 it only gains keys.

```text
{"version":1,"severity":"error","code":"E0425","message":"cannot find value `foo` in this scope",
 "labels":[{"primary":true,"message":"not found in this scope","span":{"start":8,"end":11},
 "location":{"file":"main.rs","start":{"offset":8,"line":1,"column":9},"end":{"offset":11,"line":1,"column":12}}}],
 "notes":[],"help":[],"suggestions":[]}
```

(Shown wrapped; the output is one line.)

### `Diagnostics`, the collector

```rust
use diag_lang::{Diagnostic, Diagnostics, Label, Renderer, Severity, SourceMap, Span};

let mut map = SourceMap::new();
map.add("a.txt", "abc").unwrap();
let bad = |at: u32| Diagnostic::new(Severity::Error, "bad", Label::unlabelled(Span::new(at, at + 1)));

let mut diags = Diagnostics::with_limit(2);
for at in [2, 0, 0, 1] {
    diags.push(bad(at));
}
assert_eq!((diags.error_count(), diags.len(), diags.omitted()), (3, 2, 1));
diags.sort();
assert!(Renderer::new()
    .render_all(&diags, &map)
    .ends_with("note: 1 more diagnostic not shown\n"));
```

Identical diagnostics are stored and counted once. The duplicate check is a
keyed SipHash-2-4 fingerprint (written in the crate) in an ordered index, so it
stays `O(log n)` even when an attacker controls the message text. Past the
limit, diagnostics are counted but not stored, so memory is bounded whatever the
input.

## Behaviour changes

None for existing code. `Diagnostic`'s `Debug` output gains `code` and
`suggestions` after the 1.0 fields, and equality compares them (both empty for
a 1.0-style diagnostic).

## Known limitation

In a multi-source map, source-lang 1.x lays sources out back to back: the end of
one source and the start of the next are the same position. The renderer
attributes an edit there to the next source, as it does labels, while
`apply_fixes` (which selects edits by the inclusive range `base..=base + len`,
so end-of-file insertions work) selects it for both sources. Only edits at
exactly that position are affected, and a single-source map has none. A test
pins the behaviour; source-lang 2.0's reserved end positions remove it.

## Not changed, on purpose

- **`Severity` stays exhaustive (F13).** Adding `#[non_exhaustive]` breaks every
  downstream exhaustive `match` (lsp-lang maps severities that way), so it is
  recorded for 2.0 in `dev/ROADMAP.md`.
- **No `serde`.** The JSON emitter covers the machine-readable case with no
  dependency.

## Performance

Construction is the hot path. Adding a field inline grew `Diagnostic` by 32
bytes and cost 2.5–7% on `construct` in criterion runs; the suggestion list was
moved behind one lazily allocated pointer (the code stays inline), so the type is
now 16 bytes larger than in 1.0. A first attempt that boxed all optional parts
made a diagnostic with notes 13–20% slower and was dropped.

Criterion A/B runs on this shared machine drifted by up to ±15% between runs of
unchanged code, so the comparison was made with an interleaved harness instead:
1.0.1 (from `git archive` of the v1.0.1 commit) and 1.1.0 linked into one release
binary (fat LTO), 200 alternating batches each, three runs. Change in the minimum
batch time, 1.1.0 against 1.0.1 (Windows x86_64, Rust 1.95):

| Benchmark | Run 1 | Run 2 | Run 3 |
|---|---:|---:|---:|
| `construct` (one-label diagnostic, ~40 ns) | +0.4% | +0.9% | +1.7% |
| construct with a note and a help line (~130 ns) | +1.7% | +4.6% | +1.6% |
| `render` (~410 ns) | +0.5% | +0.3% | +1.0% |
| `render_whole_file/50k_lines` (~0.9 µs) | +0.2% | −0.1% | +0.5% |

All within 5%, most within 2%. A quiet-machine criterion comparison is still
owed.

The new paths (criterion means, same machine, `cargo bench`):

| Benchmark | What it measures | Time |
|---|---|---:|
| `construct_with_code_and_fix` | A coded diagnostic with a one-edit suggestion. | ~233 ns |
| `render_with_code_and_fix` | Rendering it, suggestion block included. | ~1.56 µs |
| `to_json` | Its JSON. | ~0.91 µs |
| `collect/push_100k_twice` | 100,000 diagnostics at 100 positions, each pushed twice (clone included). | ~109 ms |
| `collect/sort_100k` | Sorting 100,000 stored diagnostics. | ~16 ms |
| `apply_edits/100k_edits` | 100,000 insertions into a 2 MB text. | ~4.2 ms |
